# POPPŌ MEMBER PORTAL 1.0 リリース管理

## 開発・反映方針
残りの機能は portal/release-1.0 ブランチで統合する。機能単位で稼働中のCloudflare Workerを更新しない。全機能の実装とリリース前確認の完了後、mainへ取り込み、固定コミットのWorkerコード・必要なD1マイグレーション・環境変数設定をまとめて案内する。既存の運営OAuth Workerは変更しない。

## 1.0 リリース条件
- 認証・アカウント発行、招待、停止・再開、パスワード変更・再設定。100000回PBKDF2検証版の安全性を再評価し、無料プランでの実行可能性と十分な対策を確認する。
- ダッシュボード、本人のプロフィール下書き・申請・取り下げ、運営の承認・差し戻し、非公開アバター提出・運営確認・公開処理。
- 配信予定の本人管理、GitHubへの競合安全な公開処理、既存CMSとの整合性。
- 活動記録・記念日、運営からのお知らせ、各種申請、申請履歴。
- 権限・CSRF・セッション失効・入力検証・アップロードの安全性・公開データの競合処理・D1移行のテスト。
- 既存データを保持した統合テスト。正式公開は検証終了後。

## 配信予定の開発状況
release-dev-v11: 本人のmemberIdとレコードidで登録・更新・削除を制御する。既存の所有者IDなしの公開予定は閲覧のみ。GitHub Contents APIのblob SHAによる競合検知を使用する。書き込みにはPORTAL_PUBLICATION_ENABLED=trueとWorker Secret GITHUB_PUBLISH_TOKENが必要で、初期状態では無効。トークンは公式リポジトリのみに限定した必要最小限の権限と有効期限を使用する。実トークンをGitHubやチャットに保存しない。Pagesの反映遅延があり得る。
現段階は構文チェックのみ。Cloudflare実行、GitHub書き込み、既存CMSとの競合、セキュリティは未検証。公開用変数はまだ設定しない。

## リリース前の運用
現在のWorkerをそのまま維持する。追加SQLやWorkerの差し替えを個別に要求しない。D1の追加設定は既存テーブル・アカウントを保持する追記型の移行としてまとめる。GitHubの保護ルールは維持する。Cloudflare上でしか確認できないテストは最終の検証デプロイ後に行う。必要な修正があれば正式開放前に対応する。

## release-dev-v14 統合状況
活動記録・記念日（本人の非公開記録）、メンバー向けお知らせと既読管理、休止・再開・退所・その他申請、運営審査、プロフィールと画像の公開ジョブ、アカウント設定、運営によるメンバー再招待、重要操作監査、ダッシュボードの未読件数を実装。画像の承認は画像と talents.json を同一 Git コミットとして非強制 ref 更新する。通信不明時の照合機能を用意したが、未確定ジョブの安全な解除手順は別途検証が必要。公開は引き続き既定で無効。

### 一括移行
install-v1.sql は migrations/0001〜0005 の追記型統合。12テーブル・11監査トリガー。既存アカウントを保持する。移行前にはD1バックアップを確認する。Cloudflare D1上の実行試験は未実施。

### 最終検証用設定（まだ設定しない）
- DB: 既存D1 binding。
- PASSWORD_PEPPER: 安全な乱数32バイトを64桁hexで表現したWorker Secret。秘密値はバックアップを安全に保持する。紛失すると新方式のパスワード検証ができなくなる。値はGitHubやチャットに置かない。
- PORTAL_TEST_MODE: true は管理された検証専用。旧パスワードの互換性は維持。新規・変更パスワードは20文字以上、HMAC-SHA256 + PBKDF2-SHA256 100000回。これは無料プラン互換性検証の設定であり、本番に十分と判定していない。パスワード変更はKDFを2回実行するためCPU制約を試験する。
- PORTAL_PUBLICATION_ENABLED: false または未設定を初期値とする。GITHUB_PUBLISH_TOKEN は公開連携試験時のみ設定。公式リポジトリへの限定トークン、Contents最小権限。公開前に保護ルールとトークンの利用範囲を確認する。
- BOOTSTRAP_SECRET: 管理者作成後は不要。既存管理者の復旧は運用手順の追加が必要。

### 確認済み
JavaScript構文解析。模擬DB・模擬Web APIによる10項目（スキーマ有効判定、未認証の運営画面拒否・メンバー画面リダイレクト、メンバーの運営審査拒否、テストモード無効時の画像・ホーム制限、HTMLエスケープ、不正日付、最低パスワード長、未対応画像拒否）。暗号・実D1・実HTTP・GitHub公開・ブラウザ動作の試験ではない。

### リリース前の残作業
本番公開の許可条件、パスワード復旧・pepper管理、画像の実デコード/寸法・メタデータ等の安全性、公開処理の競合/未確定結果の復旧、既存CMSの更新との整合性、D1移行・全認証経路・権限・スマホ表示を確認する。追加の修正は統合ブランチにまとめる。稼働中Workerの差し替えを要求しない。

## release-candidate-v15
一括導入の検証候補。画像は512KiB以下、縦横2048px以下のPNG/JPEG/WebP静止画を対象とし、構造・寸法および既知のメタデータ用コンテナを検査する。完全デコード、全メタデータ除去、マルウェア検査ではない。公開前に運営が実画像を確認すること。公開処理直前にbranch headを再確認し、結果不明の処理はロックを維持する。ロック解除は公開を停止し実行中リクエストがないこと、対象コミットのmainへの到達状況を確認した上で個別対応する。
tools/recover-admin.py は既存管理者専用のオフライン復旧補助。信頼できるPCのみで使用し、Workerを停止しD1バックアップを確保してから、対象管理者IDを確認し出力SQLを適用する。pepperを紛失した場合、全新方式アカウントの再設定が必要。秘密値と出力SQLは共有しない。
ローカル検証: 構文、画像ヘッダー・構造4ケース、取得したDDLを再現したSQLiteで12テーブル・11トリガー、一括移行の再実行、既存管理者の保持、承認操作監査、外部キー検査。実D1および実画像のデコード試験ではない。
導入時は公開更新を無効にした状態から開始する。PBKDF2 100000回は依然として互換性検証用であり、本番強度の認定ではない。メンバー一般公開は実環境の認証・権限・公開処理・画像・移行テストと安全性評価が終了するまで不可。

## release-integration-v17（2026-11-26）
PR #2でmainの公式HP・CMSをリリース用ブランチへ取り込んだ（mainへのマージではない）。配信予定の管理区分をscheduleSourceで明示する。新規ポータル登録はmember、新規CMS登録と従来の区分なしデータはadmin相当。本人編集・削除はmemberかつ公開中、memberId一致、有効なUUID、重複なしの場合のみ許可する。運営は全件編集でき、本人管理のまま内容を修正することも、明示的な運営管理への切替も可能。対象メンバーの変更・非公開化時はadminへ移す。非公開予定は本人側の公開予定閲覧に出さない。区分未設定の既存レコードを本人管理へ自動移行しない。既存配信予定のJSONは変更していない。公開JSONにメールアドレス・D1アカウントIDは格納しない。
ポータルの公開はmainの同一コミットSHAでtalents.jsonとschedule.jsonを読み、編集時のschedule blob SHAを照合する。Git tree/commitを作成後、headと有効アカウントを再確認し、非強制ref更新で競合を拒否。ref更新結果が不明な場合は再登録せず最新一覧を確認する。CMSは従来の公開データ比較とContents SHAによる競合防止を維持する。mainとの同時更新、通信断時の再試行、アカウント停止と公開の競合は実環境検証が必要。
16項目の権限・CMS保存・模擬Git/DB検証とJS構文確認済み。実環境への書き込みなし。公開連携はテスト限定。活動実績・記念日の公開申請、認証・復旧、実D1/ブラウザ検証、正式公開条件が残る。
